## 3条核心要点

### 🟢 要点一：FinBERT-Crypto情绪打分的6个结构性缺陷 — 模型本身在制造误报

C2原始定位：用FinBERT-Crypto对推文做正向/中性/负向三分类，消除70%闲聊误报。

**C2-Re视角升级**：FinBERT本身有6个结构性缺陷，每个都在系统性注入误报：

#### 缺陷1：训练数据分布偏差（最常见误报源）

| 维度 | FinBERT标准训练集 | 加密货币推文真实分布 | 冲突 |
|:----|:-----------------|:-------------------|:-----|
| 行业分布 | 通用金融(Bloomberg/Reuters) | 梗图/Meme/技术术语混杂 | 模型对"TO THE MOON"在下跌行情中的反讽标为positive |
| 时间分布 | 2018-2022训练数据 | 2026年推文风格已变（AI Agent推文/Meme币新梗） | 模型过时，对新叙事("AI Agent coins")敏感度低 |
| 语言密度 | 正式英文 | 首字母缩写/Emoji/短句("lfg", "ngmi", "wagmi", "🚀🚀🚀") | Emoji高密度被误判为positive，实际常是反讽 |
| 标签质量 | 机械众包标注 | 加密货币推文需要领域专家标注 | "This coin is going to die fast"是客观事实还是负面？ |
| 词汇偏移 | 通用金融terms | "rug", "dump", "rekt"在币圈有特定含义 | 模型将"got rekt"标为negative（正确），但将"I'm gonna buy the dip"标为positive（正确）→ 但"I bought the dip and got rekt"就矛盾 |

**源头预防方案（非末端过滤）**：

```markdown
## L0：FinBERT输入预处理（源头净化）

### 0.1 Emoji预处理映射表
| Emoji模式 | 映射 | 原因 |
|:----------|:-----|:------|
| 🚀🚀🚀(连续3+) | 忽略emoji，仅分析文本 | 连续emoji多为情绪表达，干扰语义分析 |
| 💀 | 标记potential_negative上下文 | 多数情况与"coin is dead"关联 |
| 📉📈 | 保留但标记为price_mention | 跟随市场价格走势，非KOL观点 |
| 🤡 | 标记反讽高概率 | 几乎总是反讽上下文 |

### 0.2 领域词汇白名单
```
已确认的币圈特有表达及其真实情绪方向：
  "lfg" → 正面（"let's fucking go"）
  "ngmi" → 负面（"not gonna make it"）
  "wagmi" → 正面（"we're all gonna make it"）
  "rekt" → 负面（遭受损失）
  "go to zero" → 负面（即使语法上是"go"）
  "bearish as fuck" → 强烈负面
  "moon soon" → 需判断：上涨行情→正面，下跌行情→可能反讽
```

### 0.3 反讽探测前置规则
```
前置反讽检测，通过后再走FinBERT：
  条件1：正面词 + 最近24h该币种价格跌幅>10% → 高概率反讽
  条件2：正面词 + 最近1h有负面新闻 → 高概率反讽  
  条件3："time to buy" + 可验证的KOL近30天准确率<40% → 标记低可信度
```

#### 缺陷2：输出标签过于粗糙（3分类vs需求粒度）

FinBERT输出positive/neutral/negative三分类，但A7需要更细的粒度：

```
当前：positive / neutral / negative
需要：
  - strong_buy（坚定看好，有具体价位/原因）
  - cautious_buy（看好但有条件）  
  - neutral_with_bias（倾向看多但不明确）
  - neutral
  - neutral_with_bias（倾向看空但不明确）
  - cautious_sell（看空但有条件）
  - strong_sell（坚定看空，有具体原因/事件）
  - sarcastic_positive（反讽正面——误报高发区）
  - event_driven（事件驱动，非情绪——如"Binance listed X"）
```

**源头预防**：不是增加后处理分类器，而是修改FinBERT的输出层结构，从3-class softmax改为9-class输出。

#### 缺陷3：无上下文窗口

FinBERT单条推文分析，但KOL的推文需要上下文窗口：

- Elon发"I'm bearish on BTC" 3分钟后发"just kidding lol" → 单条分析都正确，但上下文忽略了互文性
- CZ发"Attention Binancians"（中性）→ 后续发"BUSD delisting"（负面）→ 单独看第一条全是噪音，第二条才是信号

**源头预防**：FinBERT调用前先做会话窗口聚合——同一个KOL在60分钟内的推文作为一个处理单元，互文性检查后再进FinBERT。

#### 缺陷4：无币种关联（情绪打给谁？）

FinBERT只输出情绪方向，不输出关联币种。但舆情信号最核心的价值是"哪个币被情绪影响"。

**源头预防**：FinBERT前增加NER（命名实体识别）前置层，将情绪归因到具体币种。不使用独立NER模型（额外算力），而是在FinBERT tokenizer层嵌入币种符号字典（~200个活跃币种symbol+全名）。

```python
# 概念实现：嵌入层标注币种提及
class CryptoSentimentInput:
    """在输入FinBERT前置处理"""
    
    KNOWN_SYMBOLS = {
        'BTC': 'bitcoin', 'ETH': 'ethereum', 'SOL': 'solana',
        'DOGE': 'dogecoin', 'XRP': 'ripple', 'ADA': 'cardano',
        # ... 全部200+活跃币种
    }
    
    def preprocess(self, text: str) -> dict:
        mentioned_coins = []
        for symbol, name in self.KNOWN_SYMBOLS.items():
            if symbol in text.upper() or name in text.lower():
                mentioned_coins.append(symbol)
        return {
            'text': text,
            'mentioned_coins': mentioned_coins,
            'coin_count': len(mentioned_coins)
        }
```

#### 缺陷5：无训练数据持续更新（模型漂移）

FinBERT-Crypto的训练数据截止到某个时间点，但crypto社区的用语和梗不断进化。

**源头预防**：不是定期重新训练全模型（成本高），而是用**增量更新模块**：
- 每两周从ZH复盘中提取误判案例
- 使用active learning策略选择最有信息量的误判样本
- 只微调最后的分类层（adapter tuning），保持预训练权重不变

#### 缺陷6：无置信度校准（过于自信的误判）

FinBERT对positive分类的输出概率通常>0.95，即使上下文明显不确定。高置信度的错误分类更难被后续过滤捕获。

**源头预防**：实现temperature scaling置信度校准：
```python
def calibrate_confidence(logits: np.ndarray, temperature: float = 0.8) -> np.ndarray:
    """降低过分自信的logits，让不确定的输出反映到概率上"""
    scaled_logits = logits / temperature
    exp_logits = np.exp(scaled_logits - np.max(scaled_logits))
    return exp_logits / exp_logits.sum()
```
校准后，误判样本的置信度会从0.95降至0.6-0.7，暴露给后续过滤机制。

#### 汇总：6个源头的误报贡献率

| 缺陷 | 源头 | 贡献误报率 | 源头预防效果 |
|:----|:-----|:---------:|:----------:|
| 训练数据偏差 | 通用金融vs币圈语言差 | ~25% | 领域词汇表+Emoji映射 → 减少80% |
| 3分类粒度过粗 | 反讽/事件/不确定混为一谈 | ~15% | 9分类输出层 → 减少90% |
| 无上下文窗口 | 单条推文互文性丢失 | ~10% | 60min会话聚合 → 减少70% |
| 无币种关联 | 情绪无法归因到具体币 | ~10% | NER嵌入层 → 减少100%（归属问题） |
| 模型漂移 | 训练数据过时 | ~5% | 增量adapter tuning → 减少80% |
| 置信度不校准 | 错误的高置信度误判 | ~5% | temperature scaling → 减少60% |
| **合计** | | **~70%** | **源头预处理后降至~10%** |

### 🟢 要点二：多源交叉验证的4个隐蔽缺陷 — 你以为交叉了，实际上没交叉

C2原始定位：权重≥10的告警增加Reddit/币圈社群同方向情绪确认，消除30%孤立喊单误报。

**C2-Re视角升级**：多源交叉验证本身有4个结构性缺陷，导致"看似交叉了实际上没交叉"。

#### 缺陷1：来源共谋偏差（社交茧房效应）

**问题**：Reddit r/CryptoCurrency和Twitter Crypto推特圈高度重叠——同一批KOL在多个平台发文。表面上"多源确认"，实际上这3个来源都引用了同一个人的观点。

```
现实中：
  Elon发推"buy BTC" 
  → Twitter 100条转发 → A7发现"Twitter有100条正面情绪"
  → Reddit 30条讨论帖 → A7发现"Reddit也有讨论"
  结论："多源共振" → 告警
  
本质：
  100条Twitter转发 + 30条Reddit帖子 ← 全部源于Elon同一条推文
  这不是多源共振，这是单源多平台传播
```

**源头预防**：不能只是"检查有N个来源"，而要"检查N个来源是否有独立信号源"。

```markdown
## 源头预防：独立信号源计数（Independent Source Counting, ISC）

### ISC算法
1. 聚合24h内同一主题的所有消息
2. 对每条消息追溯原始发布者
3. 如果N条消息都引用了同一原始发布者 → 计为1个独立源
4. 独立源≥3才判定为多源共振

### 示例
| 场景 | 原始来源数 | 表现来源数 | 判定 |
|:----|:---------:|:---------:|:----|
| Elon说buy BTC → 100条转推 | 1 | 101 | ❌ 单源传播 |
| Elon说buy BTC + Saylor说buy BTC + CZ说buy BTC | 3 | 3+ | ✅ 真多源共振 |
| 匿名推文 → 被KOL A转发 → KOL B转发KOL A | 1 | 3 | ❌ 单源链式传播 |

### A7实施
- 不需要完整追溯图（计算量大）
- 简化：阈值策略，只检查权重≥6的KOL是否为原始来源
- 如果某个主题80%以上的消息都引用同一个人 → 独立源计数器=1
```

#### 缺陷2：时序错配（Z≠X+Y）

**问题**：来源A在08:00发推，来源B在08:05呼应，A7在08:10检查时发现"两源共振"——但B只是简单地引用了A，没有独立判断。

**源头预防**：交叉验证引入**时序窗口+因果方向**：

```
单独推文 → 作为"信号源"
引用转推 → 作为"信号传播"（不是独立源）
独立观点 → 作为"独立源"
```

```
正确做法：
  ① 先检查每条消息是否是原创
  ② 原创才计为独立源
  ③ 转发/引用/引用评论不计入独立源计数
  ④ 独立源≥3且24h独立发布 → 真多源共振
```

#### 缺陷3：来源选择偏差（幸存者偏差）

**问题**：A7当前只能覆盖大型英文社交媒体（Twitter/Reddit）。但：
- 中文社群（微信/币世界）的影响力被完全忽略
- Telegram社群（许多Meme币的主要讨论场所）不可达
- 韩国社群（UPbit/Bithumb交易对的定价中心）被忽略

**后果**：A7的多源验证只在"A7可达的来源范围内"工作，不知道不可达来源里已经有共识了。

**源头预防**：不解决所有来源的不可能。在alert.md中标注"覆盖范围偏差"：

```markdown
## 覆盖范围声明（集成到每个alert底部）
| 覆盖源 | 状态 | 权重 |
|:-------|:----:|:----:|
| Twitter/X | ✅ 覆盖 | 主要 |
| Reddit | ✅ 覆盖 | 辅助 |
| 中文社群 | ❌ 未覆盖 | 潜在盲区 |
| Telegram | ❌ 未覆盖 | 潜在盲区 |
| 韩国社群 | ❌ 未覆盖 | 潜在盲区 |
```

#### 缺陷4：验证权重不区分"独立确认"vs"随波逐流"

**问题**：当前系统对每个验证来源赋予相同权重——Twitter的1条正面推文=Reddit的1条正面帖=1个验证计数。但：

- 10万粉丝KOL的1条推文 ≠ 路人甲的1条推文
- 某币的持仓大户发言 ≠ 无持仓路人的发言
- Bull market中的看多发言 ≠ Bear market中的看多发言

**源头预防**：引入**验证来源加权体系**：

```markdown
## 验证来源权重

| 验证类型 | 权重 | 条件 |
|:--------|:---:|:-----|
| KOL原创推文 | 3x | KOL权重≥3才计 |
| KOL转推（原文来自他人） | 1.5x | 需标记原始来源 |
| 普通账户原创观点 | 1x | — |
| 社群聚合（多人同方向） | 2x | ≥5个独立账户才计 |
| 链上数据佐证 | 4x | 大额转账/合约变化可查 |
| 新闻媒体报道 | 2x | 需不是转载KOL观点 |

多源确认阈值：加权分数≥6才判定为多源共振
```

### 🟢 要点三：时间衰减权重的3个误报模式 — 时间本身不是过滤器

C2原始定位：score = initial_weight × 0.85^(elapsed_min/15)，衰减至阈值以下退出一级告警，消除旧闻在新渠道重复触发告警。

**C2-Re视角升级**：这个简单的指数衰减模型有3个结构性缺陷，在特定场景下成为误报源。

#### 缺陷1：线性衰减不匹配现实事件的影响曲线

**问题**：0.85^(t/15) 意味着：
- 15分钟后：权重降为85%
- 1小时后：降为52%
- 2小时后：降为27%
- 4小时后：降为7%

但现实中，不同类型的事件影响曲线完全不同：

```
事件类型 → 影响曲线
━━━━━━━━━━━━━━━━━━━━━━━━━━━
黑客攻击 ($100M+) 
  ─────── 初期恐慌 → 快速衰减（1-2h后市场消化）→ 但清算合约可能持续
  匹配衰减模型？ ✅ 基本匹配

监管禁令（SEC起诉）
  ─────── 初期剧烈反应 → 中期稳定 → 事件持续发酵（听证会/罚款）数周
  匹配衰减模型？ ❌ 需要高原曲线

KOL喊单（Elon说DOGE）
  ─────── 瞬时跳涨 → 快速衰减（30min内）→ 没有持续影响
  匹配衰减模型？ ✅ 基本匹配

重大升级/硬分叉（以太坊合并）
  ─────── 慢热 → 持续升温（接近日期时达到顶峰）→ 事件后缓慢衰减
  匹配衰减模型？ ❌ 需要上升→衰减曲线
```

**源头预防**：不是改衰减系数，是**为不同事件类型设计不同衰减**：

```markdown
## 事件类型特定衰减曲线

| 事件类型 | 衰减函数 | 参数说明 | 适用场景 |
|:--------|:--------|:--------|:--------|
| KOL喊单 | exp(-λt) | λ=0.1/min | 瞬时响应，30min内消失 |
| 黑客攻击 | exp(-λt) + ε | ε=0.1 | 快速衰减但残留恐慌，持续4h |
| 监管事件 | 1 / (1+λt) | λ=0.02/min | 慢衰减，持续数天 |
| 重大升级 | t×exp(-λt) | 峰值在t=1/λ | 临近事件升温，事后衰减 |
| 情绪恐慌(F&G) | exp(-λt)+β×sin(ωt) | β=0.1, ω=2π/24h | 有24h周期节律 |

### 事件类型自动识别
通过关键词检测自动分派衰减函数：
- hack/exploit/breach → 黑客衰减
- SEC/CFTC/government ban/regulation → 监管衰减
- upgrade/mainnet/hard fork/launch → 升级衰减
- buy/sell/pump/dump[币种] → KOL喊单衰减
- fear/greed/F&G → 情绪衰减
```

#### 缺陷2：衰减后的"幽灵信号"重复触发

**问题**：一条推文的score衰减到阈值以下后退出告警。但当同类事件被不同来源重复报道时，原事件的score已经低了，新事件又没有达到独立告警的阈值——实际上两件事是同一件事，但系统把它们当作独立事件处理。

```
场景：SEC起诉Coinbase
  来源A (08:00): score=60 告警
  来源B (08:15): score=51 继续告警
  来源C (08:30): score=43 继续告警
  来源D (09:00): score=31 已低于阈值40 → 退出告警
  
  来源E (09:30): 报道"SEC起诉Coinbase最新进展"
    → 新事件独立计算score
    → 但语义上是同一事件！系统产生重复告警
```

**源头预防**：用**内容摘要hash做语义去重**，而不是URL去重：

```markdown
### 语义去重：内容摘要hash

不是:
  dedup_key = URL  // URL不同=新事件 → 重复

而是:
  dedup_key = SHA256(摘要前100 chars) // 同一事件不同报道=同一key

具体：
  Step 1: 取事件描述前100个字符
  Step 2: 去除数字、标点、空格（"SEC起诉Coinbase" vs "SEC正式起诉Coinbase" → 同一事件）
  Step 3: SHA256 hash
  Step 4: 如果hash在24h内存过 → 更新原事件的score为新旧max（不是叠加）
  Step 5: 如果hash是新 → 作为独立事件创建

#### 衰减状态重置规则
- 同一事件的新报道 → 重置衰减时间基点（不是叠加分数）
- 同一事件的原始来源更新（KOL追加推文）→ 重置衰减基点
- 不同事件的引用旧事件 → 保持原事件衰减状态不变
```

#### 缺陷3：衰减阈值固定 = 在波动期灵敏度不足，在平静期过度敏感

**问题**：固定阈值（如score=40为告警下限）在波动时期（如BTC日波动5%）误报增多，在平静时期（如BTC整理期）漏报重要信号。

**源头预防**：动态阈值 = 市场波动率自适应：

```markdown
### ATR自适应衰减阈值

阈值 = base_threshold × (1 + α × (ATR(14) - baseline_ATR) / baseline_ATR)

参数：
  - base_threshold = 40（基础告警阈值）
  - ATR(14) = 当前14日均线真实波幅
  - baseline_ATR = 过去30天平均ATR
  - α = 0.5（敏感度系数，控制自适应强度）

示例：
  - 平静期：ATR=baseline_ATR → 阈值=40
  - 波动期：ATR=2×baseline_ATR → 阈值=40×(1+0.5×1)=60（更严格）
  - 极端平静：ATR=0.5×baseline_ATR → 阈值=40×(1+0.5×(-0.5))=30（更宽松）
  
效果：牛市/波动期减少误报，熊市/整理期不漏信号。
```
