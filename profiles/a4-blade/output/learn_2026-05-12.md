## 一、核心概念：风控不是"阻止交易"，是"让交易活着"

> "The first rule of trading: don't lose money. The second rule: don't forget the first rule." — 风控的本质是生存。

### 风控三层架构

| 层级 | 阶段 | 职责 | A4对应 |
|:----|:-----|:-----|:-------|
| L1 | **交易前检查** | 检查条件是否满足再下单 | 四查执行法（FK/余额/API/价格） |
| L2 | **交易中监控** | 下单过程中实时监控异常 | 滑点检测、成交确认 |
| L3 | **交易后审计** | 事后核对+异常追溯 | TRADES.md + daily.log |

## 二、量化风控指标

### 2.1 最大回撤 (Maximum Drawdown, MDD)

```
MDD = (波峰价值 - 波谷价值) / 波峰价值 × 100%
```

- 散户通常设 **20%硬止损**（账户总资金）
- 专业基金设 **10-15%** 预警线
- **A4现状：** 每笔$15（占总资金$59.90 ≈ 25%/笔）→ 风险偏高，需控制单笔损失

### 2.2 风险价值 (Value at Risk, VaR)

> "在95%置信水平下，一天内最大可能损失不超过X%"

- 计算方式：历史模拟法 / 方差-协方差法 / 蒙特卡洛模拟
- **散户简化版：** "我能承受这笔交易归零吗？" → 每笔风险金额 = 入场价 - 止损价 × 数量
- **A4应用：** A3报告中的止损价是硬约束，价格超±2%跳过的本质就是VaR控制

### 2.3 夏普比率 (Sharpe Ratio) 与盈亏比

```
Sharpe Ratio = (收益率 - 无风险利率) / 标准差
盈亏比 = 平均盈利 / 平均亏损
```

- 盈亏比≥2:1 且 胜率≥40% 是稳健系统的底线
- **A4约束：** 价格区间±2%本质上限制了单笔亏损幅度

## 三、仓位管理方法

### 3.1 凯利公式 (Kelly Criterion)

```
f* = (bp - q) / b
其中：
  f* = 最优仓位比例
  b = 盈亏比（赔率）
  p = 胜率
  q = 1 - p = 败率
```

- 例：胜率60%，盈亏比2:1 → f* = (2×0.6 - 0.4)/2 = 40%
- **警告：** 凯利公式对输入错误极度敏感，实战常用 **半凯利(1/2 Kelly)** 保守执行
- **A4现状：** 每笔$15固定（≈3.5笔余量），属于保守固定比例法

### 3.2 固定风险比例法 (固定% per trade)

| 风险偏好 | 每笔风险 | 可执行次数(总$59.90) |
|:---------|:---------|:--------------------|
| 保守 | 2% ($1.20) | 50笔（不可能，有最小执行量） |
| 中等 | 5% ($3.00) | 20笔 |
| 激进 | 10% ($6.00) | 10笔 |
| **A4当前** | **25% ($15)** | **3笔** |

> **发现：** A4每笔$15占总额25%，属于激进偏保守之间的灰色地带。建议后续纳入风控改进项。

## 四、自动化风控检查清单（Checklist 设计）

### 4.1 航空业Checklist的启示

The Checklist Manifesto (Atul Gawande) 的核心理念：
1. **简单** — 清单不是操作手册，是记忆辅助
2. **可测** — 每项检查必须能明确回答"通过/不通过"
3. **按顺序** — 关键项前置（起飞前检查引擎，不是起飞后）
4. **团队协作** — 不同角色交叉检查（A3定价格，A4查区间，FK管否决）

### 4.2 交易风控Checklist（给A4用）

```
□ [FK-01] veto.json 检查 — veto=true? → 跳过
□ [BAL-01] USDT余额 ≥ $15? → 不足则跳过
□ [API-01] AWS SSH连接可用? → 重试3次
□ [API-02] 价格查询返回正常? → 异常写ERRORS
□ [PRC-01] 当前价在A3建仓价×(1±2%)内? → 偏离则跳过
□ [ORD-01] 订单已提交? → 确认成交ID
□ [ORD-02] 成交价滑点 ≤ X%? → 异常记录
□ [LOG-01] TRADES.md已更新? → 必须写
□ [LOG-02] daily.log已追加? → 必须写
```

### 4.3 降级策略（Graceful Degradation）

| 检查失败 | 动作 | 通知 |
|:---------|:-----|:----:|
| FK veto | 停止本轮全部执行 | 记录 |
| 余额不足 | 跳过本轮 | 记录 |
| 单币价格超区间 | 跳过该币，检查下一个 | 记录 |
| API超时×1 | 等5秒重试 | 不记录 |
| API超时×2 | 等15秒重试 | 不记录 |
| API超时×3 | 等30秒重试 | 写ERRORS.md |

> **关键原则：** 降级不是失败。有记录的降级是稳健系统的标志。

## 五、进阶风控机制

### 5.1 熔断机制 (Circuit Breaker)

| 触发器 | 动作 | 恢复条件 |
|:-------|:-----|:---------|
| 连续2笔亏损 | 暂停执行1小时 | 下一节点自动重试 |
| 日亏损 > 10% | 当日停止所有交易 | 隔日07:00自动恢复 |
| 单笔亏损 > 30% | 紧急停止+通知ZH | 人工确认后恢复 |

### 5.2 多数据源交叉验证

- 价格数据源至少2个（币安API + 备用）
- 偏差>1%时触发警告
- **A4当前：** aws_executor.py 已实现4层兜底价格查询

### 5.3 禁止交易清单

- 新上线<7天的币种（流动性风险）
- 24H成交量<$100K的币种（滑点风险）
- 已被FK标记的币种
