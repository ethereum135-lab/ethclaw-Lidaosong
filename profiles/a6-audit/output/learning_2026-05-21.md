## 学到的3个要点

### 要点1：Blameless（无指责）文化 — 审计的"心理安全地基"不建就会被砸

**Atlassian 的核心方法论：**

> "在无指责的事故复盘(postmortem)中，我们不问'谁做错了'，而是问'系统的哪个环节让人做了错误的选择'。"

**关键原则：**
1. 假设每个参与者在当时的信息条件下都做了**最好的选择**
2. 目标是**找出系统漏洞**，而非**找出犯错的个人**
3. 追责文化会导致隐瞒——员工不敢承认问题，问题就永远不暴露
4. 无指责 ≠ 不追究责任——而是把责任从"个人失误"转移到"系统改善"

**对A6的映射（对照当前系统状态）：**

| 场景 | 传统审计反应 | 无指责审计反应（Blameless） |
|:-----|:-----------|:---------------------------|
| A4在03:43无A3报告时自选买入NEAR/OP/ZRO/FET/DYM 5仓违反"不自选"修正 | "A4违规操作" | "为什么A3报告07:00才出？03:43-06:32共3小时无A3输入时A4有没有更好的替代方案？信号系统有没有自动过滤机制？" |
| FK风控文件3天未更新 | "FK失职" | "FK状态文件是否需要更新？风控逻辑在TRADES.md每个节点都显示实时判断（veto=false），可能状态文件不是FK的核心功能。需要确认：FK的判断来自内存/API直查还是文件读取？" |
| 系统连续亏损31.2% | "策略失败" | "系统的哪个环节导致了亏损集中？是选币库更新中断(cron故障)？是止损执行延迟？还是RL5冻结导致资金无效12天？" |

**对A6的实际价值：**
A6的审计报告如果写得像"指控书"，即使数据准确也会被抵触。审计报告应该：
- 说"发现了X问题" 而不是 "谁导致了X问题"
- 每个问题后面跟"系统层面可以做Y改进" 而不是 "建议追责Z"

**A6报告的措辞转换示例：**
```
❌ “A4违规自选，偏差扩大”
✅ “03:43-06:32共3小时A3未产出报告期间，A4因缺少输入源使用了自选信号——建议补充『无A3报告时自动切换安全模式』逻辑”
```

### 要点2：按严重性分级触发审计流程 — 亏损期每日快检的正确性被外部方法论验证

**Atlassian 建议的触发机制：**
> "不是所有事故都做完全postmortem——按严重性阈值分级触发。Sev-1及以上强制触发，低严重性可选。"

行业标准（与Postmortem方法论一致）：

| 严重性 | 定义 | 审计流程 | 对应ZQ |
|:------|:-----|:---------|:-------|
| Sev-1 | 系统崩溃/重大亏损 | 完整深度审计 | 亏损>15% → 每日快检+保留周审计 |
| Sev-2 | 部分降级/中度亏损 | 标准审计 | 正常亏损5-15% |
| Sev-3 | 轻微影响/小亏损 | 可选审计 | 亏损<5% → 每周标准审计 |

**对A6的实际验证价值：**
- ✅ 05-17复盘补充的「亏损期每日快检规则」与Atlassian方法论一致
- ✅ 每日快检(精简版) = Sev-1触发的高频率快速检查
- ✅ 每周完整审计(深度版) = 标准质量评估(不因亏损取消)
- ✅ 周二/周四学习日与快检并行 = 在快节奏中保持能力提升

**需要补充的gap：**
当前每日快检的恢复条件（"连续3天亏损<-1%/day"）的定义不够精确：
- 什么是"亏损"？是按日P&L还是总P&L变动？
- -1%/day的base是什么？当日总资？还是本金$430的1%=$4.3？
- 建议明确：按当日P&L/当日总资 < -1%（即$2.96/day）

### 要点3：度量驱动的审计 — 从"一次性偏差率"升级为"趋势追踪+系统级指标"

**Atlassian 的建议：**
> "Capture metrics in your incident postmortem → track if your team is headed in the right direction. With consistent metrics being measured, you can take a step back and look at incident trends over time."

推荐的度量体系：

| 度量 | 定义 | A6当前 | 待扩展 |
|:-----|:------|:-------|:-------|
| MTTR（平均恢复时间） | 从事故开始到恢复的平均时间 | ❌ 无 | 对交易系统=亏损仓位的平均持有到止损/回正的时长 |
| MTBF（平均故障间隔） | 两次事故之间的平均时间 | ❌ 无 | 对交易系统=两次连续亏损之间的平均天数 |
| 偏差率趋势 | 偏差率随时间的变化方向 | 🟡 有单周数据无趋势 | 累积4周偏差率数据 → 趋势线(↑稳定↓) |
| 严重性分布 | 各种严重性级别的占比 | ❌ 无 | 🔴/🟡/🟢偏差的分布比例 |
| 经验值转化率 | 经验值多大程度转化为代码改动 | ❌ 无 | A5 output中哪些经验变成了引擎改动 |

**对A6的实际映射：**

当前A6报告中的偏差率是一个"快照"（本周X%）。但真正的审计价值在于趋势分析：

```
第1周 第2周 第3周 第4周
 4.2%  3.8%  3.1%  2.7%  → 🟢 偏差率稳定下降，系统在改善
 4.2%  4.5%  5.1%  6.8%  → 🔴 偏差率持续上升，有系统性问题
```

**对A6实操层面：**
1. 不需要新工具——每次审计报告记一个"偏差率趋势"行
2. 不需要改cron——每周一记一次，4周后就有4个数据点
3. 最简单的起步：在报告中加一行：
```markdown
| 指标 | 本周 | 上周 | 趋势 |
|:-----|:----:|:----:|:----:|
| 偏差率 | 3.2% | 2.8% | ↑(恶化) |
| 经验值覆盖率 | 100% | 95% | ↑(改善) |
```

**MTTR对交易系统的映射（对亏损期的特殊价值）：**

在亏损期，最有价值的度量不是偏差率，而是：
```
Position MTTR = 从买入到止损/回正的时间
```
如果一个POSITION的MTTR很长（>48h），说明要么A4不执行止损，要么止损机制有bug。A6需要审计的"止损执行延迟"在TRADES.md中已有数据（每笔交易的P&L和退出原因），只需要加一个提取步骤。

## 怎么让A6的审计质量更高？

### 1. 建立Blameless审计报告措辞规范

当前A6报告通过"事实陈述"已经做到了相对中立，但没有明确的措辞规范。建议增加：

**审计报告措辞规则（写入AGENTS.md）：**
| ❌ 不要 | ✅ 改用 |
|:--------|:--------|
| "A4违规自选" | "03:43-06:32无A3报告期间A4使用了自选信号" |
| "FK风控停更3天" | "FK状态文件最后更新05-18,需要确认这是技术设计还是异常" |
| "偏差率上升" | "偏差率从X%升至Y%,趋势恶化,需要根因分析" |
| "系统亏损31%" | "总资从$430降至$296(-31.2%),需要检查:选币库中断/RL5冻结/止损延迟" |

### 2. 建立4周偏差率趋势追踪

结合05-14学习的"偏差类型分类体系(L2)",在下一次审计报告中将偏差率从单周快照升级为趋势线：

**第一步（本周可做）：** 在报告中增加：
- 本周偏差率 → 上周偏差率 → 趋势(↑↓→)
- 偏差类型分布(数据/规则/环境/逻辑)

**第二步（下周可做）：** 
- 建立`profiles/a6-audit/output/trend_deviation.json`作为趋势数据库
- 每周一执行审计后自动写入一条记录
- 4周后就可以画出趋势图

### 3. 将FK状态文件停滞纳入审计风险的"系统元检查"

当前审计覆盖:
- A3/A4/A5 → 已覆盖 ✅
- FK风控 → ❌ 未覆盖（这是05-17复盘发现的gap）

本次每日快检发现fk.json更新于05-18(3天前)，但TRADES.md每个节点都显示FK实时判断正常。这说明：
- **fk.json不更新 ≠ FK不工作**
- A6需要一个机制区分"文件不更新是正常设计"和"文件不更新是异常"

**建议的元检查规则：**
```python
def check_agent_health(agent_state_path, agent_name):
    """检查Agent状态文件是否在其预期更新时间范围内"""
    last_update = get_file_mtime(agent_state_path)
    hours_since = (now - last_update).total_seconds() / 3600
    expected_interval = EXPECTED_INTERVALS[agent_name]  # 由config.yaml定义
    tolerance = expected_interval * 3  # 容忍3倍预期间隔
    if hours_since > tolerance:
        return f"🔴 {agent_name}状态文件{hours_since:.0f}h未更新(预期{expected_interval}h)"
    else:
        return f"🟢 {agent_name}正常"
```

### 4. 引入"经验值转化率"作为A5审计的补充维度

当前A5审计只看覆盖率（SELL是否都有对应JSON）。覆盖率100%是好的，但不代表A5的经验值真正被用了。

建议新增审计维度：
```
经验值转化率 = 被引擎引用的经验值数 / 总经验值数 × 100%
```
这个指标比覆盖率更接近审计的本质：不是"做没做完"，而是"做的有没有用"。

### 5. 亏损期专有审计：持仓MTTR监控

当前每日快检覆盖了USDT闲置率、风控健康度、A3→A4阻塞、止损延迟。建议补充：
```
平均持仓时长(按仓位类型):
- A3买入仓位: X小时
- STRONG自选仓位: X小时  
- 整体平均: X小时

异常标记:
- 如果某个仓位持仓>48h → 🔴 检查止损机制是否阻塞
- 如果平均持仓<30min → 🔴 系统可能在做高频低价值交易
```

从当前TRADES.md数据看, 05-21的仓位(A3买入DASH)和自选仓位(NEAR/OP/ZRO/FET/DYM)都不存在超长持仓问题，但05-19之前有大量持仓被RL5冻结无法退出。MTTR在RL5冻结期间飙升是不可控的，应在审计中标记为"环境因素"而非"A4执行力问题"。

## 学习总结

> 第二轮学习审计方法论（审计方法论第二轮轮换: 所有4主题覆盖后从Topic1重新开始），这次深入的是Blameless文化和度量驱动两个新维度，而非重复第一轮(5 Whys/三层偏差/三线模型)。
>
> **Blameless文化**提供了审计的"心理安全地基"：审计报告措辞从"谁做错了"转向"系统哪个环节允许了这个错误"。这个转变对亏损期尤为重要——总资-31.2%的系统中，追责只会让Agent更不敢报问题，从而让问题隐藏。
>
> **分级触发机制**验证了05-17补充的亏损期每日快检规则的合理性——行业标准的Sev-1触发模式。
>
> **度量驱动**提出了从"单周快照"升级为"4周趋势线"的路线图，以及MTTR(持仓恢复时间)作为亏损期核心审计指标的概念。
>
> 最重要的一点：**亏损期A6的最大价值不是增加审计项，而是提供一个心理安全的报告环境**——让系统不是怕A6，而是在A6的报告中看到改进的方向。
