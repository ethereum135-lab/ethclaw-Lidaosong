## 学到的3个要点

### 要点1：审计闭环的「收口机制」— 发现≠修复，修复≠验证

**核心洞察（来自Atlassian Postmortem Guide + ZQ实操）：**

Atlassian明确指出：「一张未经审阅的复盘报告（postmortem）等于从未写过。」（*An unreviewed incident postmortem report might as well never have been written.*）

这映射到A6审计的一个根本缺陷：**A6持续发现A3→A4管道断裂，但这7天来没有任何「收口」机制。**

```
当前状态（05-21到05-28）：

A6发现管道断裂 ──→ 周报标记🔴 ──→ ZH被告知 ──→ 无修复动作 ──→ 下周一再发现管道断裂
      ↑                                                               │
      └────────────────────── 空转循环 ────────────────────────────────┘
```

**标准审计闭环应包含4个阶段：**

| 阶段 | 描述 | ZQ系统当前状态 |
|:----|:------|:--------------:|
| ① 发现（Detect） | A6通过偏差分析发现异常 | ✅ A6已连续3次报告A3→A4管道断裂 |
| ② 报告（Report） | 审计报告送达决策者 | ✅ weekly_audit.md已投递 |
| ③ 修复（Fix） | 决策者（ZH/老李）制定并实施修复 | ❌ **缺失** — 无人采取行动 |
| ④ 验证（Verify） | A6在下周审计中验证修复效果 | ❌ **无法进行** — 无修复可验证 |

**Atlassian的阈值触发机制（Tip 1 — Set a threshold）：** 不是每个问题都要走完整闭环。组织应定义严重级别阈值，达到阈值自动触发postmortem流程。

**对A6的映射：** 对于连续3周（3次审计）都被标记🔴的A3→A4管道断裂问题，应定义「升级协议」：
- 第1次🔴 → 标准报告标记
- 第2次🔴 → 加「ZH必须回应」标记
- 第3次🔴 → 升级为「系统性风险」，触发强制ZH回复机制

### 要点2：5 Whys的「常见误用防御」— 为什么A3→A4管道断裂5次审计都没有修复

**Atlassian 5 Whys Defense 的关键洞见：**

原文从5个维度批评和辩护5 Whys方法论，其中最切中ZQ系统痛点的三点：

**① 不要停在「人」的层面（Objection: blame culture）：**
> 「永远不要把人当作根因。人为错误、B组的失误、员工X注意力不足——这些都不是可接受的答案。什么导致了人为错误？什么过程导致了B组的失误？」

ZQ系统的A3→A4管道断裂，如果停在「A4没执行A3推荐」「A4自选买了GENIUS」——这是停在「人/代理层面」的根因。A6需要追问更深：
- Why 1: A4为什么没执行A3推荐的AR/MDX？ → 因为A4按signals.json信号扫描执行，而非A3报告
- Why 2: 为什么A4按signals.json而非A3报告？ → 系统存在两套并行信号源且优先级未定义
- Why 3: 为什么优先级未定义？ → A4规则中「A3报告优先」的修正是口头约定而非代码级别强制
- Why 4: 为什么口头约定而非代码强制？ → A4引擎没有「检查A3报告→优先执行」的硬逻辑
- Why 5: 为什么没有硬逻辑？ → 系统架构层: A3和A4是两套独立引擎，之间没有执行管道

**② 「5」不是字面数字（Objection: 5 is too many/too few）：**
> 「5是简写，不是字面数字。有时候3个why就够了，有时候需要7个。关键是持续挖掘到背后的流程缺陷。」

A6的偏差分析目前只到第1-2层Why（「A4没执行A3推荐」「偏差率N/A」），没有继续往下挖到系统架构层。Round 2学习的「强制停机点」标签应该配合这个原则：**不到架构/策略级的不算到底。**

**③ 根因链可以分叉（Objection: single root cause）：**
> 「没有规则说最终根因必须是一个。5 Whys不是线性追问，因果链可以变成树状。」

A3→A4管道的根因不止一条：
```
根因链A（信号源冲突）:
A3产出推荐 → A4也用signals.json → 两源竞争 → prioritize未定义

根因链B（仓位限制）:
3仓上限 → XLM/RIF/JTO占满 → 无插槽执行A3推荐 → A4只清理了XPL/EUL而非弱信号仓

根因链C（止损不坚决）:
JTO(0pts❌)持续占用仓位 → RIF(58pts⚠️)未退出 → 无资金部署A3推荐

根因链D（引擎架构）:
A3是独立分析Agent → A4是独立执行Agent → 之间只有"建议"关系，没有"指令"关系
```

A6应该在审计报告中明确标注分叉的根因链，而非只写「管道断裂」。

### 要点3：Postmortem的度量与趋势追踪 — A6如何从「点检」升级为「趋势引擎」

**Atlassian的度量建议（Tip 7 — Capture incident metrics）：**
> 在postmortem中追踪硬数据：停机分钟数、严重等级、MTTR（平均恢复时间）。有了这些指标，可以判断团队是否在往正确方向前进。

**对A6的映射：** 当前审计是「点检模式」——每次只看本周数据，没有累积趋势分析。这导致连续3次报告A3→A4管道断裂，但报告中看不出「恶化了还是改善了」。

**建议引入4项趋势指标：**

| 趋势指标 | 当前 | 上周 | 趋势 | 含义 |
|:---------|:----:|:----:|:----:|:-----|
| A3→A4执行率 | 0/3=0% | 0/5=0% | → | 持续断裂无改善 |
| 自选买入占比 | 1笔/今日 | ~3笔/日 | ↓ | 有所减少(但第一天) |
| 🔴红灯持续性 | 连续3周 | 连续2周 | ↑恶化 | 问题正在固化 |
| USDT闲置率趋势 | 33.7% | ~40% | ↓改善 | 资金部署效率提升 |

**Atlassian的阈值机制（Tip 1 — Set a threshold）：** 结合趋势追踪，A6可以定义「可接受趋势」：
- 🔴红灯数从3周前的3个降到本周的1个→🟢改善
- 🔴红灯数从3周前的3个维持在3个→🔴恶化
- 🔴红灯数从3周前的3个变成本周4个→🔴恶化+新问题出现

**实操建议：** 在weekly_audit.md尾部追加「趋势面板」：
```markdown
## 趋势面板（多周累积）

| 指标 | 05-11 | 05-18 | 05-25 | 趋势 |
|:-----|:----:|:----:|:----:|:----:|
| 偏差率判定 | 🟢 | 🟡 | 🔴 | ↓恶化 |
| 覆盖率 | 🟢 | 🟢 | 🟢 | →稳定 |
| 🔴红灯数 | 1 | 2 | 3 | ↑增加 |
| 总资 | ~$430 | ~$350 | ~$315 | ↓下滑 |
```

这可以让ZH/老李一眼看出系统趋势，不用翻多周报告才能判断。

## 怎么让A6的审计质量更高？

### 1. 建立「审计闭环」的收口追踪机制

当前A6的审计是「知更鸟模式」——报告完就结束了，不追踪修复。

**建议引入「3轮审计+升级」规则：**

```markdown
问题首次发现(审计N):
  → 标记🔴 + 标准报告 → 期待ZH行动

同一问题再次发现(审计N+1):
  → 标记🔴 + 「重复发现」标签 + 要求ZH明确回应时间

同一问题第三次发现(审计N+2):
  → 升级为「系统性风险」+ 自动通知链（A6→ZH→老李）+
    A6在报告中建议具体修复方案
```

**当前A3→A4管道断裂状态检查：**
- 05-25 首次发现 → ✅ 已报告
- 05-27 第二次发现 → ✅ 已报告+重复标记
- 05-28 第三次发现 → ⚠️ **应触发「系统性风险」升级**

### 2. 在偏差报告中引入「根因分叉链」而非单一结论

当前A6的偏差分析只输出「管道断裂🔴」——太粗。

**建议格式：**
```markdown
### 偏差分析：A3→A4管道断裂（连续第3次报告）

🔴 系统性问题 — 根因分叉分析：

① 信号源冲突（架构级）
   证据: A3推荐+signals.json并行, A4优先后者
   建议: 统一信号路由管道, A3报告→A4执行队列

② 仓位轮出规则缺失（策略级）
   证据: JTO(0pts❌)/RIF(58pts)长期占用仓位
   建议: 设定弱信号仓强制轮出规则(<20pts持续2节点)

③ 止损不坚决（执行级）
   证据: JTO已0pts但未止损/轮出
   建议: A4执行止损时检查仓位信号质量, 0pts强制退出
```

### 3. 审计报告引入「趋势面板」替代单次快照

每周一完整审计和亏损期每日快检都应加入趋势数据：
- 不再是「本周偏差率=多少」
- 而是「偏差率趋势：从05-21的🟢→05-25的🟡→05-28的🔴」
- 一眼可见系统是「改善」「稳定」还是「恶化」

**这比任何单周指标都更能反映系统真实健康状况。**

## 学习总结

> 第四轮学习审计方法论（第四轮——从第一轮「是什么」→第二轮「怎么做」→第三轮「做得对不对」→本轮「做了之后呢？」）。本轮聚焦Atlassian Postmortem Guide中关于审计闭环、度量追踪、趋势分析的核心理念。
>
> **① 审计闭环的收口** — 发现≠修复，修复≠验证。A3→A4管道断裂连续3次报告无人修复，说明系统缺少「收口机制」。应引入3轮审计+升级规则：首次标记→再次要求回应→第三次自动升级。
>
> **② 5 Whys的深层追问** — 不要停在「A4没执行A3推荐」的表面根因。追问到信号源冲突、仓位轮出规则缺失、止损不坚决这三个分叉根因链。根因链可以分叉，不追求单一答案。
>
> **③ 趋势面板替代单次快照** — 每次审计都在周报告中追加趋势数据（偏差率/红灯数/总资的多周对比）。让读者一眼看到「改善」「稳定」还是「恶化」的方向，而不是单周数据。
>
> **对A6的直接影响：** 下一份完整审计报告（下周一/05-29）应包含：①趋势面板（多周偏差率/红灯数/总资对比）；② 对A3→A4管道断裂的「第3次报告→自动升级」声明；③ 根因分叉分析（4条根因链）；④ 建议具体修复方案而非仅标记问题。
