## 🔑 要点一：管道架构重构 — 从"全桥SSH"到"本地直连+分级降级"

**核心问题：** A8当前9路数据采集**全部依赖AWS SSH隧道**（`3.27.3.202`）。一旦SSH超时（如当前状态），全部9路同时报错，信号产出为零。这是一个单点故障（SPOF）架构。

**根本矛盾：** 当初设计通过AWS SSH的原因是被Mac防火墙封锁加密API出站。但以下API已被验证**从本地Mac可直接访问**（无需AWS隧道）：

| 数据源 | 本地可达性 | 验证时间 |
|:-------|:---------:|:--------|
| DeFiLlama `/v2/chains` | ✅ 本地curl直通 | 2026-06-09 08:00 |
| CoinGecko `/v3/global` | ✅ TCP可连 | 2026-05-15已验证 |
| **所有仅需HTTP的公开API** | **需逐一路径验证** | 待执行 |

**解决方案 — 三级数据源架构：**

```
层级        数据源                             优先级   依赖
L0-本地     DeFiLlama, CoinGecko公开端点       最高     ❌ 零依赖
L1-AWS桥    DexScreener, Etherscan V2          中       ✅ 需SSH
L2-付费桥   BSC/Arb钱包API, Dune查询           低       ✅ 需SSH+Key
```

**立即可行的动作：**
1. 在`a8_data_fetch.py`中新增`step 0` — 从本地Mac直接curl DeFiLlama获取链级TVL（零依赖，已验证可通）
2. 修改`main()`的执行逻辑：不再一次性等待AWS桥失败，而是**先跑L0本地数据**，再跑L1-AWS桥
3. 当AWS桥失败时（SSH超时），L0级数据仍然写入snapshot，`data_quality`字段改为`"⚠️ 部分受限(AWS桥不可达,仅L0数据可用)"`
4. 逐一路径验证本地Mac可直接访问的其他API端点

**预期效果：** 即使AWS桥持续不可达，A8至少能产出链级TVL数据（DeFiLlama），而非全部为空数组。信号覆盖从0%恢复至40%+。

## 🔑 要点二：信号降噪与有效性提升 — 从"全量采集"到"前置过滤"

**核心问题：** A8当前是"先采集全部数据，再过滤出信号"。采集9路数据耗时90s，但经常产出0条可用信号（因为选币库的币不在成交量TOP中时，所有INFLOW信号为空）。大量计算资源浪费在采集不用的数据上。

**行业最佳实践分析：** 实时数据管道（如Apache Flink/Kafka Streams、Chainlink Data Feeds等高频数据系统的共同设计模式）遵循三个原则：

### 原则1：前置过滤/预筛选

A8应该从"全量采集→后过滤"改为"预筛选→定向采集"：

```
现在:  固定9路 → 全部采集 → 后过滤 → 产出信号(90s)
优化:  读选币库 → 预筛选买盘币 → 只查这N个币 → 产出信号(30s)
```

**具体实现：**
- 步骤顺序调整：**先读选币库/牛币库** → 提取活跃交易币种清单（通常30-50个） → 只针对这些币去DexScreener查成交量
- 不再做全网大额转账扫描（90条MONEY_IN汇总成一行即可 → 从步骤③中按需过滤）
- 选币库为空时的回退列表（BTC/ETH/SOL/XRP/DOGE/PEPE/BNB/SUI/LINK/AAVE）前置硬编码到脚本第一行

### 原则2：信号分级缓存

A8当前每15分钟完整扫描一轮，但**大部分信号的历史趋势变化很小**。利用缓存减少重复计算：

```
缓存策略:
  TVL数据: 每1小时更新一次（变化慢，每小时最多差±2%）
  大额转账: 每5分钟更新（变化快，但只有10%的时间有新高）
  DEX成交量: 每15分钟更新（适中）
```

**具体实现：**
- `data/a8/cache/` 目录存储历史快照
- 新增`compare_with_cache()`函数：对比当前与缓存差异，差异<阈值时跳过写入
- 变化率>阈值=写入信号+更新缓存；变化小=不写入（节省A3读取成本）

### 原则3：信号归一化与去重

当前A8的多路数据（INFLOW/MONEY_IN/基础数据）格式不统一，下游A3读的时候需要额外解析。**每条信号应该格式统一，便于A3直接读取：**

```
统一信号格式（所有数据源产出同一种dict）:
{
  "signal_type": "INFLOW|MONEY_IN|CHAIN_TVL|LENDING|BRIDGE",
  "pair": "BTC/USDT",
  "chain": "ethereum",
  "value": 50000,          # 成交额/USDT数/TVL变化
  "reason": "成交额>$50K|USDT转账>$500K|TVL24h+5%",
  "confidence": "high|mid|low",
  "timestamp": "2026-06-09T08:00:00+08:00"
}
```

这样A3的`step 0.5`直接按`signal_type`和`confidence`过滤，不需要解析复杂管道数据。

**预期效果：** 执行时间从90s降至30-40s，信号有用率从30%提升至80%+。

## 🔑 要点三：零故障架构设计 — SSH不可达时的智能降级与自动恢复

**核心问题：** 当前A8管道设计是"要么全通，要么全断"。一旦AWS SSH超时（如今天早晨的状态），整个A8管道产出全部为空信号。这与"每15分钟必有产出"的承诺矛盾。

**行业分析：** 实时金融数据系统中的"熔断器模式"（Circuit Breaker Pattern）是处理外部依赖不可达的标准方案。结合A8的实际架构：

### 熔断器三层设计

```
数据源状态机（每个数据源独立）:
  ✅ HEALTHY → 正常采集，写入snapshot
  ⚠️ DEGRADED → 采集失败，使用上次成功缓存数据（有效期1小时）
  ❌ DOWN → 标记"数据源不可达"，跳过采集，不阻塞其他数据源
```

**具体实现：**

1. **每个数据源独立熔断器** — 失败时立即降级为缓存数据，不影响其他8路
2. **智能重试** — 第一次失败后，等待30秒再试（不立即重试，避免压垮AWS SSH）
3. **渐进退避** — 连续失败：5分钟→15分钟→30分钟递增间隔，避免频繁重试
4. **健康探测** — 即使数据源标记为DOWN，每30分钟自动尝试恢复连接
5. **缓存老化** — 缓存有效期：链TVL数据1小时、大额转账数据30分钟、成交量数据15分钟

### 状态监控与自愈

在`a8_data_fetch.py`启动时新增健康检测阶段：

```
step -1: SSH隧道探测
  ① 尝试SSH连接AWS（ConnectTimeout=5s）
  ② 成功 → 标记AWS桥：HEALTHY
  ③ 失败 → 跳过所有AWS桥数据源（L1+L2），只走L0本地路径
  ④ state写入 `ssh_bridge_status: "HEALTHY|DOWN"`
  
  → 这步只需5秒，不是90秒。如果AWS桥不通，直接跳过，不求等待。
```

**同时修复当前SSH超时问题（优先级P0）：**

根据SSH verbose输出，TCP连接已建立但banner exchange超时。常见原因：
1. AWS EC2 SSH daemon过载 → 重启SSHD或EC2实例
2. 安全组带宽限制 → 检查AWS CloudWatch
3. 本地代理干扰SSH协议 → 检查`/etc/ssh/crypto.conf`中是否有非标准配置

**临时应急方案：** 当SSH完全不可达时，部分数据源（如DeFiLlama、Etherscan V2 API）可**直接从本地Mac的SOCKS5隧道**或其他代理访问，不依赖AWS。需逐一验证。

**预期效果：** AWS桥断连时，A8不再全部产出空信号。至少产出L0级链TVL数据（DeFiLlama），信号恢复率从0%提升至40%+，且数据源故障清晰标注，不编造。
