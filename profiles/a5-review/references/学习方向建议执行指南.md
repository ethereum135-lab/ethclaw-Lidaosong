## 第二步：薄弱环节识别判断树

### 判断流程

```
读取全部数据源
       ↓
计算三个维度的风险分
       ↓
     ┌──┬──┐
   入场  退出  选币
   质量  质量  质量
     │    │    │
   ┌─┴─┐ ┌─┴─┐ ┌─┴─┐
   好  差  好  差  好  差
```

### 维度1: 入场质量判断

**触发条件**（满足任一即判定"入场质量差"）：

| 条件 | 阈值 | 计算方式 | 代码示例 |
|:-----|:----:|:---------|:---------|
| 亏损交易占比高 | > 50% | 亏损笔数 / 总交易笔数 × 100% | 66/115 = 57.4% → 亏损占比高 |
| 平均亏损幅度大 | < -3% | 所有亏损交易P&L的均值 | -7.71% → 远超阈值 |
| 严重亏损笔数多 | > 5笔 | P&L < -5%的交易计数 | 11笔严重亏损 |
| 重复亏损币种多 | ≥ 3个币种各亏≥2次 | 同一个币种多次亏损且平均P&L为负 | ASTER(4次均-1.17%), TON(5次均-5.6%) |

**入场质量差 → 是TOP1薄弱环节的判断条件：**
```
亏损交易占比 > 50% 且 平均亏损 < -3%
  → 入场问题是TOP1
```

### 维度2: 退出质量判断

**触发条件**（满足任一即判定"退出质量差"）：

| 条件 | 阈值 | 计算方式 |
|:-----|:----:|:---------|
| E2+E3占总退出比例高 | > 60% | (E2退出数 + E3退出数) / 总退出数 × 100% |
| E系列信号正确率低 | < 10% | 各信号的正确次数 / 触发总次数 |
| too_early退出占比高 | > 50% | 标记为too_early的退出 / 总退出数 |
| 错误退出率高于正确退出率 | 错误 > 正确 | 错误退出计数 > 正确退出计数 |

**退出质量差 → 是TOP1薄弱环节的判断条件：**
```
E2+E3占比 > 60% 且 E系列信号正确率 < 10%
  → 退出问题是TOP1
```

### 维度3: 选币质量判断

**触发条件**（满足任一即判定"选币质量差"）：

| 条件 | 阈值 | 计算方式 |
|:-----|:----:|:---------|
| 经验库中"需改进"占比高 | > 80% | 需改进经验数 / 总经验数 × 100% |
| 最差币种持续出现 | ≥ 5个币种 | 亏损Top5币种在多个时间段重复出现 |
| 选币准确率低 | < 30% | 推荐后24h盈利币种 / 总推荐币种 |

**选币质量差 → 是TOP1薄弱环节的判断条件：**
```
"需改进"经验占比 > 83%
  → 选币问题是长期基础问题（但不是紧急TOP1，除非其他两维度都好）
```

### 综合优先级排序

```
入场质量差 和 退出质量差 同时存在
  → 检查因果链：入场差 → 导致被套 → E2/E3误触退出
  → TOP1通常是"入场质量"
  → 因为改善入场位置后，E2/E3误触自然减少

入场质量好 但 退出质量差
  → TOP1是"退出质量"

入场质量差 但 退出质量好（很少见）
  → TOP1是"入场质量"

三个都差
  → TOP1=入场(根因), TOP2=退出(结果), TOP3=选币(基础)
```

## 🔷 专业升级一：PDCA循环应用于系统改进（第二步：薄弱环节识别后执行）

### PDCA循环框架

> PDCA（Plan-Do-Check-Act）是戴明提出的持续改进方法论。A5在识别薄弱环节后，不是只输出一次建议就结束——而是启动一个闭环改进循环。

```
P[Plan: 识别问题 → 建议学习方向] --> D[Do: A5学习这个方向]
D --> C[Check: 一段时间后检查改善效果]
C --> A{有效?}
A -->|是| Act1[Act: 制度化/标准化]
A -->|否| Act2[Act: 换方向/重新Plan]
Act1 --> P_next[下一轮Plan]
Act2 --> P_next
```

### A5中的PDCA实现

**P — Plan（计划）**
- 什么时候做：每天23:00学习方向建议时
- 做什么：
  1. 读取近期监督评估+工具评估数据
  2. 识别当前最薄弱的环节（入场/退出/选币）
  3. 确定1-3个学习方向
  4. 写入 `建议ZH学习方向_YYYY-MM-DD.md`
- 输出：学习方向建议（含数据支撑和预期改善）

**D — Do（执行）**
- 什么时候做：建议发出后，A5开始学习和应用
- 做什么：
  1. A5深入阅读该方向的专业资料
  2. 将学到的知识应用到监督评估中
  3. 触发下游（ZH）关注该方向
- 记录：在 `profiles/a5-review/output/learning_YYYY-MM-DD.md` 中记录学习进度

**C — Check（检查）**
- 什么时候做：建议发出N天后（N=7/14/30天，根据问题严重程度）
- 做什么：
  1. 重新计算该方向的关键指标
  2. 对比建议发出前的基线数据
  3. 判断是否改善
- 输出：`PDCA检查_YYYY-MM-DD.md`

**A — Act（处理）**
- 有效 → **制度化**：
  - 把有效的改进写入系统标准/规则
  - 记录在经验档案中
  - 标记该方向为"已解决"
- 无效 → **换方向**：
  - 分析为什么没效果（是学错了/时间不够/问题不是根因？）
  - 重新Plan，换新的学习方向
  - 如果连续3次PDCA都无效 → 标记为"系统硬伤"（见动态跟踪）

### PDCA记录模板

```markdown
## PDCA循环记录 — 学习方向名

### P (Plan)

- 建议内容: [具体学习方向]

- 学习内容: [学了的专业资料/方法]
- 应用情况: [是否已应用到监督评估中]

### C (Check)
- 检查日期: YYYY-MM-DD
- 检查周期: N 天
- 当前数据: [关键指标对比基线]
- 改善幅度: [量化变化]
- 判定: ✅已改善 / ⚠️没有明显变化 / ❌反而恶化

### A (Act)
- 判定: ✅制度化 / 🔄继续观察 / ❌换方向
- 下一步行动: [具体行动]
```

## 第五步：根因链分析（写报告前必须做）

不要照搬工具输出的排名。工具只算统计量，你需要判断因果链：

```
现象层（工具输出）：
  亏损占比57.4%
  E2/E3误触71.7%
  选币84%需改进

逻辑层（手动判断）：
  入场差 → 买在高位 → 价格一回调就触发E2/E3 → 过早退出 → 亏损积累
            ↓                      ↓
        高频too_early          错误退出多
            ↓                      ↓
        经验库标记              选币看起来差
        "需改进"                (但根因是入场而非选币)

结论：
  TOP1根因 = 入场质量
  TOP2结果 = 退出质量（入场差的副产品）
  TOP3问题 = 选币质量（长期基础问题）
```

### 三种常见因果链模式

| 模式 | 现象 | 根因 | 建议关注点 |
|:-----|:------|:-----|:----------|
| 入场差→退出差 | 亏损>50% + E2/E3>60% | **入场位置不佳** | 学习入场时机优化 |
| 选币差→全亏损 | 选币准确率<20% + 全线亏损 | **选币逻辑** | 学习赛道/币种筛选 |
| 退出纪律差→盈利回吐 | 入场好但正确退出率<10% | **退出纪律** | 学习信号确认+持股耐心 |

## 🔷 专业升级二：根因分析（5 Whys法）— 第五步的强化版本

### 5 Whys方法论

> 表面现象不是根因。连续问5个"为什么"，穿透表面找到真正的根因。

现有的根因链分析（第五步）已经做了初步的因果判断，但不够深入。5 Whys法提供了一个标准化的追问流程。

### 标准5 Whys流程

```markdown
问题: [表面现象]
  ↓
为什么? (Why 1) → [第一层回答]
  ↓
为什么? (Why 2) → [第二层回答]
  ↓
为什么? (Why 3) → [第三层回答]
  ↓
为什么? (Why 4) → [第四层回答]
  ↓
为什么? (Why 5) → [根因]
```

### 实战示例：E2信号正确率1.2%

```markdown
## 5 Whys分析 — E2信号正确率低

**表面问题**: E2信号正确率仅1.2%（远低于系统要求的30%）

**Why 1**: 为什么E2正确率低？
→ 因为多数E2触发后30分钟内价格就反弹，交易被洗出

**Why 2**: 为什么30分钟就被洗出？
→ 因为E2对短期价格波动（噪声）太过敏感

**Why 3**: 为什么E2对噪声敏感？
→ 因为E2的算法设计是检测短期价格偏离，没有区分噪声与趋势变动的能力

**Why 4**: 为什么没有区分能力？
→ 因为系统退出决策依赖E2单一信号，没有与其他信号/条件交叉验证

**Why 5 (根因)**: 为什么退出决策只用E2单一信号？
→ **根因: 退出策略缺少多信号交叉验证机制；E2作为短期波动信号不应单独决定退出，应结合E1(趋势方向确认)或E4(风控)一起判断**

**改进方向:**
1. 短期: E2触发后增加E1确认条件（趋势方向一致才退出）
2. 中期: 增加E2的信号缓冲区（价格需持续偏离超过N分钟才触发）
3. 长期: 建立退出信号的权重投票机制（单信号不独立决策）
```

### 另一个实战示例：重复亏损币种

```markdown
## 5 Whys分析 — ASTER重复亏损

**表面问题**: ASTER在近7天亏损4次，平均亏损-1.17%

**Why 1**: 为什么ASTER每次都亏？
→ 因为每次买入后很快触发E2/E3退出

**Why 2**: 为什么买入后很快触发E2/E3？
→ 因为ASTER波动大，入场后短期波动就触发了退出阈值

**Why 3**: 为什么知道ASTER波动大还要买？
→ 因为选币逻辑只看赛道热度，没考虑币种波动率

**Why 4**: 为什么选币时不考虑波动率？
→ 因为当前选币维度不包括波动率指标

**Why 5 (根因)**: 为什么选币维度缺少波动率？
→ **根因: 选币评分模型只有"赛道热度"单一维度，缺少币种机制适应性的评估（高波动币种需要不同的入场/退出策略）**

**改进方向:**
1. 选币评分增加波动率维度
2. 高波动币种设置更宽的E2/E3阈值
3. 或直接排除高波动币种（如果系统策略不适合）
```

### 5 Whys在薄弱环节分析中的使用时机

| 场景 | 使用5 Whys? | 原因 |
|:-----|:-----------:|:-----|
| 单个E信号持续差 | ✅ 必须 | 找到是算法问题还是组合问题 |
| 单个币种重复亏损 | ✅ 必须 | 找到是选币问题还是策略适配问题 |
| 整体胜率下降 | ✅ 建议 | 区分是入场差还是退出差 |
| 交易频率异常 | ✅ 建议 | 找到是信号阈值问题还是策略问题 |
| 某日大幅亏损 | ⚠️ 可选 | 如果是黑天鹅事件，不需要5 Whys |
| 单笔随机亏损 | ❌ 不需要 | 单笔亏损可能是随机噪声 |

Why 1 → [回答]

## 🔷 专业升级三：因果关系 vs 相关关系的区分

### 核心原则

> 工具评估显示"a4_trend_checker装上后胜率提高" ≠ "a4_trend_checker导致胜率提高"
> 相关 ≠ 因果

A5在写学习方向建议时，必须区分哪些是因果关系，哪些只是相关关系。

### 四种常见场景

| 场景 | 关系类型 | 示例 | A5应该如何写 |
|:-----|:---------|:-----|:------------|
| 工具A接入后指标B改善+同期无其他变化 | **强因果关系** | a4_trend_checker接入后正确退出率从30%→55% | "接入a4_trend_checker后正确退出率提升25个百分点，因果关系可信" |
| 工具A接入后指标B改善+同期有其他变化 | **弱因果关系** | 新工具接入+同时市场从熊转牛+胜率提升 | "胜率提升，但同期市场环境也变化了，不能确定是工具的效果" |
| 工具A接入后指标B未变+其他指标变 | **相关关系** | 工具改善入场但没改善总P&L | "入场质量改善但未转化为收益，需要查证因果链的断裂点" |
| 无工具变化但指标B变好 | **纯相关关系** | 胜率突然提升，同期没有任何工具变更 | "胜率提升但无工具变更，可能是市场驱动，不是系统改进" |

### 因果判断自查清单

在每次写学习方向建议前，对照以下清单检查：

- [ ] 是否确定工具A在指标B改善前就已经接入？（时间顺序）
- [ ] 是否有其他同时发生的变更可能影响指标B？（混淆变量）
- [ ] 改善幅度是否超过随机波动范围？（统计显著性）
- [ ] 改善是否在多个时间段一致出现？（可重复性）
- [ ] 是否排除了市场整体走势的影响？（市场因素）

**如果5个检查项中有3个以上的答案是"不确定"或"否" → 标记为相关关系，不是因果关系。**

### 建议中的措辞规范

| 关系类型 | 推荐用语 | 禁用用语 |
|:---------|:---------|:---------|
| 强因果关系 | "接入X后，Y提升了Z%，存在因果关系" | — |
| 弱因果关系 | "接入X后，Y提升Z%，但不能排除其他因素" | "X导致Y提升" |
| 相关关系 | "Y提升了Z%，同期X已接入，存在相关关系" | "X改善了Y" |
| 纯相关 | "Y在近期提升了Z%，原因待查" | 任何归因性表述 |

## 常见错误（不要犯）

| # | 错误 | 正确做法 |
|---|------|---------|
| 1 | 把现象当根因 | "E3误触"不是根因，"入场位置差+持有时间短"才是根因 |
| 2 | 不检查因果链 | 算出统计就直接抄到报告里，没判断哪个是因哪个是果 |
| 3 | 忽略数据质量标记 | 如果DQW标记了大量污染数据，先从样本中排除再分析 |
| 4 | 样本量太小的维度也排进TOP3 | 某维度样本<10笔 → 不参与排名，标记为"数据不足" |
| 5 | 趋势判断凭感觉 | 趋势必须有数据支撑：连续N天改善/恶化才标趋势方向 |
| 6 | 风险分凭感觉 | 风险分基于统计量计算，不能随机给分 |
| 7 | 建议太笼统 | "学入场"太宽泛 → "学习多时间框架确认入场点/避免趋势末端追入" |
| 8 | 不标记UNCERTAINTY | 发现可疑数据（如-100%亏损）必须标记，不能忽略 |
| 9 | 只写问题不写建议 | 每个薄弱环节必须有对应的学习方向建议 |
| 10 | 和前一天报告完全一样 | 如果连续多天相同排名，但问题在恶化 → 标记风险升级 |
| 11 | 把运气当作分析结果 | 市场整体下跌导致的亏损 vs 入场位置差导致的亏损 — 要区分 |
| 12 | 不启动PDCA循环 | 出了建议就结束了，没有跟踪Check和Act | 每次建议必须纳入PDCA循环管理 |
| 13 | 不执行5 Whys | 停留在第一层归因（如"E3误触"），没穿透到根因 | 必须连问5个Why直到找到系统级根因 |
| 14 | 把相关当因果 | 工具接入后指标变好就认为是工具的效果 | 必须执行因果关系自查清单的5项检查 |
| 15 | 不跟踪以前建议的效果 | 每天重复输出相同的建议但没有历史对比 | 维护薄弱环节动态跟踪表，跨天对比 |
| 16 | 连续相同建议不升级 | 连续3天建议"入场优化"但数据持续恶化 | 第3次不变好→标记风险升级，第5次→标记系统硬伤 |

## 🔷 专业升级四：薄弱环节动态跟踪

### 核心原则

> 连续3次建议同一方向但无改善 → 标记为"系统硬伤"

建议不能只出一次就结束。每个学习方向建议必须从"提出→跟踪→评估→关闭"进行全生命周期管理。

### 动态跟踪记录表

在 `profiles/a5-review/output/` 下维护一个动态跟踪文件 `薄弱环节动态跟踪.md`：

```markdown
# A5 薄弱环节动态跟踪

## 跟踪记录

### 方向: [例: 入场时机优化]

| 序号 | 建议日期 | 建议内容 | 基线数据 | 是否采纳 | 7天复查 | 14天复查 | 30天复查 | 最终状态 |
|:----|:--------|:---------|:--------|:--------:|:-------:|:--------:|:--------:|:--------:|
| 1 | 05-10 | 学多时间框架入场 | 亏损率60% | ✅ | 55% 📉+5% | 58% 📈-3% | 52% 📉+8% | 🟡改善中 |
| 2 | 05-17 | 学支撑位识别 | 亏损率52% | ✅ | — | — | — | 🔄跟踪中 |
| ... | ... | ... | ... | ... | ... | ... | ... | ... |
```

### 每个建议的跟踪周期

```markdown
建议发出日 (Day 0)
  ↓
7天后 (Day 7):  首次复查 → 检查该方向关键指标是否有改善
  ↓
14天后 (Day 14): 二次复查 → 如果是短期课程，此时应看到初步效果
  ↓
30天后 (Day 30): 终期复查 → 如果是系统性改进，此时应该体现
  ↓
关闭或升级
```

### 状态标记

| 状态 | 含义 | 判定标准 |
|:-----|:------|:---------|
| ✅ 已解决 | 该方向已明显改善 | 关键指标改善 > 10个百分点 |
| 🟡 改善中 | 有改善但还不够 | 关键指标改善 3-10个百分点 |
| 🔄 跟踪中 | 刚提出，在观察期 | 从建议日算起 < 7天 |
| ⚠️ 进展慢 | 有改善但速度低于预期 | 连续14天改善 < 3个百分点 |
| ❌ 无效果 | 完全没有改善 | 连续14天改善 < 1个百分点 |
| 🚫 硬伤 | 系统级问题，多次尝试无效 | 连续3次建议同一方向但无改善 |

### "系统硬伤"判定流程

```markdown
## 系统硬伤判定

### 触发条件
同一薄弱方向连续3次被推荐，但均无明显改善

### 判定流程
1. 回溯该方向的所有建议记录
2. 确认每次建议的内容是否足够具体（不是笼统的"学入场"）
3. 确认ZH/A4是否采纳了建议（没采纳=不是系统硬伤，是执行问题）
4. 如果已采纳但连续3次无效 → 标记为"🚫 系统硬伤"

### 硬伤标记格式
🚫 系统硬伤: 入场时机优化
- 首次建议: 05-10
- 最近建议: 05-24
- 建议次数: 3次
- 采纳情况: ✅已采纳
- 累计改善: -2%（反而恶化了）
- 判定: 系统当前的策略框架无法解决此问题，需要更高层级的策略重构

### 硬伤处理方式
- 短期: 不再对该方向反复建议（换方向）
- 中期: 在月度复盘时汇报给老李/Commander
- 长期: 需要策略层级的重新设计
```

### 动态跟踪与PDCA的整合

```
PDCA每一轮 = 一个建议方向的一个完整周期

P: 提出建议，记录基线
D: A5学习，应用，触发下游
C: 7天复查 + 14天复查 + 30天复查
A: 已解决→关闭 / 无效果→换方向 / 硬伤→升级上报

薄弱环节动态跟踪 = 所有PDCA轮次的汇总记录
```

### 代码级跟踪（可选）

在 `tools/learning_suggest.py` 中集成动态跟踪逻辑：

```python
# 伪代码逻辑
tracking = load_tracking_file()
for direction in tracking.directions:
    if direction.status == "跟踪中" and direction.days_since_suggested >= 7:
        current_data = get_current_metrics(direction.metrics)
        improvement = current_data - direction.baseline
        if improvement > 10:
            direction.status = "已解决"
        elif improvement > 3:
            direction.status = "改善中"
        elif improvement < 1:
            direction.status = "无效果"
            direction.fail_count += 1
            if direction.fail_count >= 3:
                direction.status = "系统硬伤"
```
