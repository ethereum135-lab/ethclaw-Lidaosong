地基层设计 v1.0

六大系统定位的深层架构

全网调研后确认 · 解决6个地基层问题 · 定稿前最后一道关

0

全网调研的核心发现

多Agent系统失败的第一原因不是功能重叠，不是模型不够强，而是上下文不一致 — 不同Agent用不同的数据定义做决策，结果互相矛盾。

解决方案：共享上下文层 — 所有Agent读写同一个数据源，用同一套定义。
— Atlan: How to Orchestrate Multi-Agent Systems at Scale
交易安全铁律：
1. 永远不开启提现权限
2. 先用只读API Key → 模拟盘3个月 → 才开交易权限
3. 永远不在工作区文件中存API密钥
4. 必须有Kill Switch（紧急停止开关）
5. OpenClaw不适合高频交易 — 延迟在秒级
— Trading Risk & Compliance Framework
Vibe-Trading天然解决了共享上下文问题：
- Docker部署在AWS上24/7运行
- 6大数据源自动采集+降级
- 22个MCP工具可被所有平台调用
- 支持OpenClaw ClawHub一键安装
- 跨会话持久记忆+FTS5搜索
- MIT开源，支持Ollama本地零成本运行

基于以上发现，六大系统定位需要在地基层加一个"共享上下文层" — 这是之前缺失的。 Vibe-Trading不是第七个平台，而是这个共享层的基础设施。

1

谁24/7运行全球经济体？

答案：Vibe-Trading = AWS上的24/7数据+分析引擎

之前的问题是：TraeCode（我）是对话式的，不在线时全球经济体就停了。 调研后发现：Vibe-Trading可以Docker部署在AWS上24/7运行， 它内置6大数据源、29个智能体、自动采集+分析+回测。

角色 平台 运行模式 负责什么
24/7数据引擎 Vibe-Trading (AWS Docker) 持续运行 采集全球数据、美林时钟判断、29个智能体分析
策略决策者 TraeCode（我） 对话式 读Vibe-Trading分析 → 做最终决策 → 写策略给Hermes
执行者 Hermes (AWS) 持续运行 读策略配置 → 执行交易 → 回报结果

TraeCode不在线时的降级逻辑：
Vibe-Trading持续运行 → 产出分析结果存入共享上下文 → Hermes读取最后一次策略继续执行 → OpenClaw监控异常并推送告警到手机 → 我上线后复盘+调整。

Vibe-Trading的角色定义

Vibe-Trading不是第七个平台 — 它是"地基的地基"

Vibe-Trading的位置：六大平台下方的共享基础设施层。 所有平台通过它获取数据、写入结果、共享上下文。

第六层：传播层

第五层：监控层
交易异常→推送手机；社交媒体情绪抓取
OpenClaw
第四层：执行层
买卖、止损止盈、合约杠杆（后期）
Hermes
第三层：决策层
策略方向、仓位、止损止盈
TraeCode
第二层：工程层
策略代码、数据管道、扩展开发
Claude Code Codex
第一层：分析层
美林时钟、传导链、多空辩论

⬇ 地基层：共享上下文层 ⬇

Vibe-Trading

关键： Vibe-Trading在所有平台下方 — 它是基础设施，不是竞争对手。 它输出数据和初步分析 → TraeCode做最终决策 → Hermes执行 → OpenClaw监控 → WorkBuddy产出内容。 所有平台都通过MCP工具或共享文件读写Vibe-Trading的数据。

3

Hermes不只是"手" — 需要自主决策能力

Supervisor/Worker模式 — Hermes有"小脑"

调研发现：Supervisor/Worker模式的核心风险是Supervisor瓶颈 — 如果Supervisor(TraeCode)挂了，整个系统停摆。 解决方案：Worker(Hermes)必须有基于最后已知指令的自主运行能力。

场景 TraeCode在线 TraeCode不在线 降级逻辑
正常交易 TraeCode给策略 → Hermes执行 Hermes读最后策略 → 继续执行 Hermes有自己的RSI/布林/F&G策略，可独立运行
紧急止损 TraeCode判断 → 调整止损 Hermes用F&G联动止损自动执行 止损是硬编码的，不需要AI判断
新币种入场 TraeCode分析 → 选择币种 Hermes用RSI<35自动扫描入场 有自主入场逻辑，但仓位用保守默认
策略大调 TraeCode重写策略文件 等待TraeCode上线 不自主做策略大改 — 等人
Kill Switch TraeCode或人工触发 连续5笔亏损自动触发 / 人工Telegram命令 熔断是硬编码的，不需要AI
Hermes定位修正：不是纯"手"，而是有自主风控能力的执行引擎。
执行=听TraeCode的；风控=自己独立做（止损、熔断、仓位限制）。
这符合"Supervisor不在线时Worker基于最后指令自主运行"的标准模式。
4

数据在六个平台之间怎么流转？

共享上下文层 — 所有平台的单一数据源

调研发现：Agent记忆是短暂的，共享上下文层才是持久的状态存储。 所有平台不直接互相传数据 — 它们读写同一个共享层。

数据类型 谁写入 谁读取 存储位置 格式
全球宏观数据 Vibe-Trading TraeCode AWS共享目录 JSON/CSV
美林时钟状态 Vibe-Trading TraeCode + Hermes AWS共享JSON JSON
交易策略配置 TraeCode Hermes AWS策略文件 YAML/JSON
交易记录 Hermes TraeCode + OpenClaw AWS日志 JSONL/MD
告警事件 OpenClaw 手机(Telegram/微信) OpenClaw内部 消息
内容素材 TraeCode WorkBuddy 本地共享目录 Markdown
F&G/RSI指标 Hermes (API调用) Vibe-Trading + TraeCode AWS共享JSON JSON

规则：任何平台不直接调用另一个平台的内部数据。 所有数据通过共享上下文层流转 — 写入约定的文件/Redis/JSON， 其他平台按约定读取。这避免了"Agent A的定义和Agent B的定义不一致"的问题。

5

安全边界 — API密钥隔离

安全铁律 — 来自全网最佳实践
核心原则：最小权限 + 物理隔离 + Kill Switch
— 交易所API只开"读取+交易"，永远不开提现
— API密钥存在AWS环境变量，永远不在工作区文件
— 绑定服务器IP白名单
— 必须有紧急停止开关
平台 能接触什么 不能接触什么 安全措施 风险等级
Hermes 交易所API密钥（交易权限） 提现权限（永远不开） 环境变量存储+IP白名单 最高
TraeCode 读写策略配置文件 不能直接调交易所API 通过SSH改Hermes配置 中
OpenClaw 读交易日志 → 推送通知 不能触发交易、不能接触API密钥 只读权限+SOUL.md限制 低
Vibe-Trading 公开市场数据API 不能接触交易所交易密钥 数据API Key独立于交易Key 低
Codex/Claude Code 代码仓库、脚本 不能接触任何API密钥 密钥在.env文件，gitignore 中
WorkBuddy 内容素材、输出文件 不能接触交易系统 完全隔离 低
Kill Switch设计（三层熔断）：
1. Hermes自动熔断：连续5笔亏损 / 总回撤>8% → 自动停止
2. Telegram命令熔断：手机发"/killswitch HALT" → Hermes立即停所有交易
3. 人工API撤销：登录交易所 → 撤销API Key → 物理断连
6

降级方案 — 每种故障的应对

故障树 — 从最坏到最好
故障 概率 影响 应对
AWS完全宕机 极低 Hermes+Vibe-Trading全停，无法交易 OpenClaw在本地检测断连 → 推送手机告警 → 人工登录交易所撤单 → 等AWS恢复
Hermes宕机 低 交易停止，已有挂单仍在交易所 OpenClaw检测Hermes无心跳 → 推送告警 → 人工检查 → 重启
TraeCode不在线 常态 无新策略，但交易继续 Hermes用最后策略自主运行 → Vibe-Trading持续产出分析 → 我上线后复盘
Vibe-Trading数据源断 中 无新宏观数据，分析停滞 Vibe-Trading自动降级到备用数据源 → 仍有历史数据可用 → OpenClaw告警
OpenClaw挂了 低 无告警推送，交易不受影响 Hermes有自动熔断兜底 → 定期人工检查 → 重启OpenClaw
交易所API限流 中 下单失败、数据获取中断 Hermes自动指数退避重试 → 超过阈值暂停交易 → OpenClaw告警
策略持续亏损 已发生 资金减少 连续5笔亏损 → 自动熔断 → 等人工复盘修复策略
设计原则： 任何单点故障都不能导致资金损失。
交易所侧的挂单是独立于系统存在的 — 即使所有平台都挂了，交易所上的止损单仍然有效。
系统的任务不是"不能挂"，而是"挂了不会丢钱"。
